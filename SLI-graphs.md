# Графики SLI в vmui

## Подготовка

```sh
make -C infra/minikube/metrics open-ui
```

Открыть <http://localhost:8428/vmui/>, выбрать Graph, диапазон Last 30 minutes и шаг 30s. Для каждого графика ниже добавить три запроса: SLI, SLO и SLA. Все значения выражены в процентах. При совпадении SLO и SLA линии накладываются.

Запросы ниже используют демонстрационное скользящее окно 5 минут. Это не оценка SLA за календарный месяц. Для SLO заменить все `[5m]` на `[30d]`. Для SLA нужен отдельный расчёт за точный интервал календарного месяца UTC: для счётчиков — прирост за этот интервал, для проб — доля успешных измерений в нём. Скользящие 30 дней не эквивалентны календарному месяцу.

Для скорости используется существующая граница гистограммы 500 мс. Изменять приложение и пересобирать backend для этого расчёта не нужно.

Запись должна получать регулярную нагрузку валидными запросами. Без учитываемых событий график записи отсутствует, а не показывает 100%. Ниже используется согласованная политика исключений из раздела «Исключения записи»; при её изменении нужно обновить соответствующие селекторы в запросе.

## 1. Доступность каталога

SLI:

```promql
100 * avg_over_time(probe_success{job="bookshop-availability"}[5m])
```

SLO:

```promql
vector(99.5)
```

SLA:

```promql
vector(99)
```

Вспомогательные запросы:

```promql
probe_success{job="bookshop-availability"}
```

```promql
up{job="bookshop-availability"}
```

```promql
count_over_time(probe_success{job="bookshop-availability"}[5m])
```

При периоде 30 секунд ожидается около 10 измерений за 5 минут; границы окна и задержки опроса могут влиять на количество. Среднее считается только по полученным измерениям. Само по себе оно не подтверждает полноту данных: нужно также проверять историю `up` и наличие проб за весь период. `up=0` означает сбой получения метрик пробера, а `probe_success=0` при `up=1` — неуспешную проверку приложения.

## 2. Скорость чтения каталога

SLI:

```promql
100 *
sum(increase(ogen_server_duration_milliseconds_bucket{
  job="bookshop-pods",
  oas_operation="listBooks",
  http_response_status_code="200",
  le=~"500(\\.0)?"
}[5m]))
/
(
  sum(increase(ogen_server_duration_milliseconds_count{
    job="bookshop-pods",
    oas_operation="listBooks",
    http_response_status_code="200"
  }[5m])) > 0
)
```

SLO и SLA — два одинаковых запроса:

```promql
vector(95)
```

Гистограмма измеряется в миллисекундах, поэтому граница — 500, не 0.5. Ровно 500 мс входят в быстрые ответы, больше 500 мс — только в знаменатель и ухудшают SLI. Ошибочные ответы исключены из числителя и знаменателя: это показатель скорости успешных чтений, не доступности.

В общий поток входят также обращения пробера и readiness к backend через соответствующие пути. Сейчас метрик для надёжного разделения пользовательских и служебных чтений нет; данный SLI описывает все backend-вызовы `listBooks`.

## 3. Успешность записи

SLI:

```promql
100 *
(
  sum(increase(ogen_server_request_count_total{
    job="bookshop-pods",
    oas_operation=~"createBook|updateBook|createPublisher|updatePublisher",
    http_response_status_code="200"
  }[5m]))
  or
  0 * sum(increase(ogen_server_request_count_total{
    job="bookshop-pods",
    oas_operation=~"createBook|updateBook|createPublisher|updatePublisher",
    http_response_status_code!~"400|409"
  }[5m]))
)
/
(
  (
    sum(increase(ogen_server_request_count_total{
      job="bookshop-pods",
      oas_operation=~"createBook|updateBook|createPublisher|updatePublisher",
      http_response_status_code!~"400|409"
    }[5m]))
    -
    (
      sum(increase(ogen_server_request_count_total{
        job="bookshop-pods",
        oas_operation=~"updateBook|updatePublisher",
        http_response_status_code="404"
      }[5m]))
      or
      0 * sum(increase(ogen_server_request_count_total{
        job="bookshop-pods",
        oas_operation=~"createBook|updateBook|createPublisher|updatePublisher",
        http_response_status_code!~"400|409"
      }[5m]))
    )
  ) > 0
)
```

SLO и SLA — два одинаковых запроса:

```promql
vector(99)
```

`or 0 * ...` даёт нулевой числитель при наличии неуспешных запросов, но отсутствии серии успешных. Сравнение знаменателя `> 0` без `bool` исключает окна без учитываемых операций, сохраняя само значение положительного знаменателя.

Сначала вычисляется `increase` отдельно для каждой серии, затем суммы: так учитываются сбросы счётчиков при рестартах и несколько экземпляров backend.

## Исключения записи

Согласованная политика:

| Операции | Исключаемые статусы | Причина |
|---|---|---|
| Все четыре операции записи | 400 | Некорректный JSON, параметры или нарушение правил валидации |
| Все четыре операции записи | 409 | Дубликат книги/издательства; для книги также ссылка на отсутствующее издательство |
| Только `updateBook`, `updatePublisher` | 404 | Обновляемого объекта нет |

Исключённые запросы не входят ни в числитель, ни в знаменатель. Успех — только 200. Остальные наблюдаемые статусы считаются неуспехом, включая 5xx и неожиданный 404 при создании.

Эта политика использует только имеющиеся метки операции и статуса. Кодов бизнес-ошибок в метриках нет: отличить ожидаемый и ошибочно возвращённый 409 нельзя. Запросы, не распознанные маршрутизатором как одна из четырёх операций, также не входят в этот SLI. Потери до backend и недоступность HTTP-соединения покрываются пробером каталога лишь для его пути, не данным счётчиком записи.

## Сценарий скринкаста

План, пока без реализации переключателей задержки и ошибок:

1. Несколько минут выполнять успешные чтения и записи; показать исходные метрики и три SLI с линиями целей.
2. Включить задержку 600 мс именно внутри обработчика `listBooks`, чтобы её включал таймер ogen. Ответ остаётся 200, порог пробера 3 секунды не превышается. Показать падение доли чтений за 500 мс.
3. Выключить задержку, дождаться выхода медленных запросов из окна.
4. Включить управляемую внутреннюю ошибку одной операции записи, например `updatePublisher`. Продолжать отправлять валидные запросы. Показать 500 в счётчике и падение SLI записи.
5. Выключить ошибку и дождаться восстановления оконного SLI.
6. На учебном стенде временно масштабировать frontend до нуля; backend и стек метрик оставить работающими. Показать `probe_success=0` при работающем пробере.
7. Вернуть исходное число реплик frontend, дождаться готовности и показать восстановление.

Для будущих переключателей предпочтительны параметры конфигурации, выключенные по умолчанию. Не нужен открытый публичный HTTP endpoint для управления поломками. Изменение конфигурации с рестартом достаточно для учебной демонстрации, но сам рестарт тоже может влиять на доступность. Задержку лучше реализовать с учётом отмены контекста, а ошибку возвращать обычным `error`, не `panic`.

После каждого воздействия ждать обновления scrape и оконного SLI. Линии целей SLO/SLA остаются постоянными; меняются SLI и выполнение обязательств. При короткой истории нельзя утверждать, что подтверждено месячное SLA.
