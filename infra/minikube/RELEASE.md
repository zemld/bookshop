# Релиз Bookshop в Minikube

Один Git-тег задаёт версию frontend, backend и Goose. Запускайте команды из репозитория. Для примеров ниже PostgreSQL и её Service, ConfigMap и Secret, а также Service для frontend и backend уже созданы в пространстве имён `bookshop`. Скрипт использует Docker, Minikube, kubectl и jq. Для другого профиля задайте `MINIKUBE_PROFILE`.

```sh
git tag -a v0.1.0 "$release_commit" -m 'Bookshop v0.1.0'
infra/minikube/release.sh build v0.1.0
```

`release_commit` — SHA проверенного коммита. Сборка берёт исходники из коммита под тегом. Версия и полный SHA записываются в backend и frontend при сборке. Сборка напрямую из Dockerfile без аргументов сообщает `dev` и `unknown`. Опубликованный тег сохраняйте за одним коммитом. После проверки тег можно отправить командой `git push origin v0.1.0`.

## Миграции

```sh
infra/minikube/release.sh migrate v0.1.0
```

Команда запускает только Goose и ждёт успешного завершения Job. Перед запуском другой версии дождитесь окончания текущей миграции. Успешный Job сохраняется, поэтому повтор команды для того же релиза использует его результат. Если Job завершился ошибкой, проверьте `kubectl --context minikube -n bookshop logs job/migrate-v0-1-0`. После устранения причины удалите завершившийся ошибкой Job и повторите команду.

Если релиз требует изменений схемы, выполните миграции перед выкладкой. На время обновления схема должна подходить обеим версиям приложения.

## Выкладка

```sh
infra/minikube/release.sh deploy v0.1.0
```

Команда применяет манифесты frontend и backend из коммита релиза с его тегами образов по очереди. Сначала команда обновляет backend и ждёт его готовности, затем обновляет frontend. Перед сигналом завершения старый под ждёт пять секунд, чтобы Service успел перенаправить новые соединения. Для возврата к предыдущему релизу используйте его тег, если текущая схема совместима с ним.

## Проверка

- На HTTP-порту обоих сервисов `GET /livez` проверяет, что сервер отвечает. `GET /readyz` у backend возвращает `503`, если PostgreSQL недоступна. У frontend готовность зависит от его собственного HTTP-сервера.
- В VMUI выполните `bookshop_build_info{job="bookshop-pods"}`. Метрика показывает сервис, версию и SHA, а сборщик добавляет имя пода. Эти же данные доступны в стартовом логе с событием `service.build`.
- Импортируйте [Bookshop](../../docs/monitoring/bookshop-dashboard.json) и [PostgreSQL Exporter](../../docs/monitoring/postgres-exporter-dashboard.json) через интерфейс Grafana. При импорте выберите источник VictoriaMetrics. В Bookshop панель «Версии сервисов по подам» показывает версии на выбранный момент.
