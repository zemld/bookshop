# Coding standards

## Стиль кода

Придерживаемся [Uber Go Style Guide](https://github.com/uber-go/guide/blob/master/style.md).

Предпочитаем простой, линейный код с минимальной вложенностью.
Логика должна читаться сверху вниз без лишних переходов между функциями.

Переиспользуем существующий код. Вводим абстракции, когда они решают конкретную задачу.

Не пишем поясняющие комментарии в рукописном коде. Выражаем смысл через понятные имена,
структуру и небольшие функции.

Это правило не распространяется на служебные комментарии: директивы `//go:*`,
`//nolint`, `-- +goose` и маркеры сгенерированных файлов.
Не удаляем рабочие директивы.
Сгенерированный и сторонний код, включая комментарии и лицензионные уведомления,
вручную не редактируем. Сгенерированные файлы обновляем штатными генераторами.

Имена функций и методов начинаем с глагола и явно описываем действие:
`CreateOrder`, `ValidateBook`, `LoadBooks`.
Это правило распространяется на шаблоны и тестовые помощники.
Конструкторы — исключение: сохраняем привычные имена `New`, `NewServer`,
`NewHTTPServer` и их неэкспортируемые варианты.
Сохраняем имена, обязательные для языка и внешних интерфейсов:
`main`, `Error`, `Unwrap`, `ogen.Handler.NewError`.

## Ошибки

При возврате ошибки из зависимости добавляем контекст операции через
`fmt.Errorf("operation: %w", err)`, сохраняя исходную ошибку в цепочке.
Контекст должен объяснять, какая операция не удалась, а не просто повторять
сообщение исходной ошибки.

Не оборачиваем ошибки без нового полезного контекста.
Не используем `%v`, конкатенацию строк или `errors.New(err.Error())`
для оборачивания: они теряют связь с исходной ошибкой.

Для проверки конкретной ошибки используем `errors.Is`,
для получения ошибки определённого типа — `errors.As`.
Не определяем вид ошибки по тексту её сообщения.

## Архитектура

Используем Ports & Adapters.

Все доменные модели и интерфейсы доменных сервисов находятся в `domain`.
Доменные модели описывают бизнес-понятия, их поведение и инварианты.

Реализации доменных сервисов находятся в `services`.
Они организуют бизнес-сценарии и используют `ports` для взаимодействия с внешними зависимостями.

Ports — интерфейсы внешних зависимостей, к которым мы обращаемся: API, БД,
хранилищ, публикации сообщений и других операций ввода-вывода.

Adapters реализуют ports. Они отвечают за взаимодействие с внешними системами
и преобразование данных. Бизнес-правила остаются в доменных моделях и сервисах.

`domain` не зависит от `services`, `ports` и `adapters`.
`services` и `ports` не зависят от `adapters`.

Используем только интерфейсы из `domain` и `ports`.

Транспортные типы, модели хранения и типы внешних SDK остаются
на соответствующих границах системы и не проникают в доменные контракты.

Handlers и workers вызывают бизнес-логику через интерфейсы доменных сервисов.
Они не обращаются к adapters напрямую.

## Тесты

Логику покрываем тестами.
Проверяем поведение, бизнес-инварианты и обработку ошибок.

Тесты для файла `name.go` размещаем в `name_test.go`.

Тестируем сценарии поведения функции, а не детали её реализации.
Для каждой тестируемой функции создаём одну тестовую функцию:
для `ValidateBook` — `TestValidateBook`.
Все сценарии этой функции описываем табличными тесткейсами внутри неё,
а не отдельными тестовыми функциями.
Каждый тесткейс явно описывает сценарий, входные данные и ожидаемый результат.

Функции подготовки зависимостей и проверки результата определяем непосредственно
в соответствующих тесткейсах, только когда сценарию они нужны.
Не выносим сценарную подготовку и проверки в общие хелперы.
Общие для всех сценариев действия и проверки
оставляем в основном теле теста.

Для подмены зависимостей используем сгенерированные моки их интерфейсов.
Моки вручную не пишем и не редактируем.

Изменения должны сохранять существующее поведение вне своей задачи.
